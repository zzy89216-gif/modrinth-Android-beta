# ModBox 保活与 Compose 渲染调研

> 日期：2026-11-28 · 范围：Android 12+ 后台限制、厂商自启动差异、Compose 渲染优化
> 结论落地见「六、ModBox 应该怎么做」。本文只写调研结论，不做厂商自启动跳转引导
> （各家设置页入口 / 权限命名差异太大，程序化跳转不可靠，需要时引导用户手动进设置）。

---

## 一、Android 12+ 后台限制（与我们相关的事实）

1. **后台不能随意启动前台服务**（Android 12，API 31 收紧）：
   App 处于后台时调 `startForegroundService()` 会抛
   `BackgroundServiceStartNotAllowedException`（12.0 之前是静默的 ANR 风险）。
   → **我们的对策**：`DownloadManager` 只在「用户刚点了下载」的会话内启动服务
   （此时 App 在前台 / 有 Activity），启动时点一定合法；启动后靠前台服务自身保活，
   不依赖运行时再从后台拉起。
2. **前台服务必须声明 type**（Android 9+ 声明、Android 14 起强制校验）：
   数据下载用 `dataSync`，需要两个权限：
   - `android.permission.FOREGROUND_SERVICE`（28+）
   - `android.permission.FOREGROUND_SERVICE_DATA_SYNC`（29+）
   manifest 里 `<service android:foregroundServiceType="dataSync">`。
   minSdk 26 不需要 `<property android:name="android.app.PROPERTY_DATA_SYNC...">` 白名单声明（那是 34 的 `specialUse` 等类型要求，dataSync 不在此列）。
3. **POST_NOTIFICATIONS 运行时权限**（Android 13+）：
   不授予 = 前台服务的「运行中通知」不显示（服务本身能跑，但用户看不到进度，
   且 13+ 上持续无通知的前台服务会被系统标记为异常）。→ MainActivity 启动时申请一次，
   已用 `registerForActivityResult(RequestPermission())` 实现。
4. **Doze / App Standby**：
   手机熄屏 + 不移动会进 Doze，网络会被周期性切断，下载可能长时间「卡住」。
   前台服务能让 App 拿到「部分 Doze 豁免」，但不保证持续联网。
   → 产品上把下载定位为「用户在场时下载」，不强求 Doze 中完成；
   网络恢复后 OkHttp 会自然续传（我们已支持 Range 断点续传）。
5. **12+ 后台 Activity 启动限制**：
   后台不能弹 Activity。我们通知点击回 MainActivity 时 App 多半已被拉到前台，
   合法；不需要处理。

## 二、厂商自启动与电池白名单（调研结论，不实现跳转）

| 厂商 | 行为 | 对下载的影响 |
|---|---|---|
| 小米（MIUI/HyperOS） | 默认杀后台极积极；有「自启动」开关 + 「省电策略：无限制」 | 前台服务期间一般能保活；进程被杀后任务状态丢失。建议用户开自启动 + 无限制 |
| 华为（EMUI/HarmonyOS） | 默认杀后台；有「电池优化：允许后台活动 / 允许自启动」 | 同上。HarmonyOS NEXT 对第三方限制更严 |
| OPPO（ColorOS） | 中偏严；「自启动」+「省电策略：不限制」 | 前台服务基本能保活 |
| vivo（OriginOS/Funtouch） | 中偏严；「后台高耗电」+「自启动」 | 同上 |
| 三星（One UI） | 相对宽松；「不优化电池」即可 | 影响小 |
| Pixel / AOSP | 按标准 Android 策略（Doze / Standby） | 前台服务 + 通知正常 |

**结论**：
- **前台服务（dataSync）+ 持续通知 = 所有厂商下最稳的后台存活方式**，这就是我们
  DownloadService 的形态。厂商再怎么杀，前台服务有通知在栏里时被杀的概率最低。
- **自启动权限**（冷启动、开机后自动拉起）对「用户主动下载」场景**不是必需**：
  下载都是用户点出来的，App 必然在前台。只有「后台接收推送触发下载」才需要，
  我们不做。
- **电池白名单 / 省电策略**：建议在下载页放一句弱提示文案「若下载中断，请检查
  系统设置中本 App 的电池优化策略」，不做强引导跳转。
- 厂商差异太大（设置页路径、权限命名、是否可被系统 API 查询都不同），
  **不做程序化跳转引导**，只写进这份文档和提示文案。

## 三、Compose 渲染调研

### 3.1 合成与硬件加速

- Compose 内容绘制在 `RenderThread` 上走 **Skia → GPU 合成**，硬件加速在
  minSdk 26 上是**默认且强制**的（`hardwareAccelerated` 从 14 起默认开，
  26 之后无法关），不需要做任何事，也不要在 manifest 里乱写
  `android:hardwareAccelerated="false"`。
- Compose 的合成模型：`setContent` 里一棵 UI 树 → 布局/测量 → 绘制命令
  （DrawScope）→ RenderThread 录制 + GPU 光栅化。**主线程只做测量、布局和
  提交指令，不做像素绘制** —— 这是 Compose 和老 View 体系最大的区别，
  也意味着 jank 的主要来源是「主线程被测量/重组/GC 占住」，而不是绘制本身。
- 高刷屏（90/120Hz）：Compose **不强制** 120Hz。App 默认跟随系统 UI 帧率
  （Pixel 4+ 系统 UI 可设 90/120），游戏/动画场景才会申请
  `setPreferredRefreshRate` / `View.requestedFrameRateRange`。
  列表滚动这类场景按默认帧率跑即可，**不要主动锁 120**（功耗翻倍，
  且 UI 线程压力大时 120Hz 更容易掉帧出 jank）。

### 3.2 列表（LazyColumn）性能清单

| 项 | 做法 | 为什么 |
|---|---|---|
| stable key | `items(projects, key = { it.id })` | diff 时 O(1) 定位，减少重组与复用错乱 |
| stable data | 列表项数据用 data class（如 `Project`），或实现 `areContentsTheSame` 语义 | Compose 列表用值相等判断要不要重组 item |
| 固定行高 | item 用 `Modifier.height(fixed)`（ProjectCard = 76dp） | LazyColumn 预布局不用测量，滚动成本恒定 |
| 避免 item 内 state 膨胀 | 进度等高频变化值用 `derivedStateOf` 或把进度抽到子 Composable | 只重组变化的那一行 |
| 图片尺寸写死 | `AsyncImage` + `Modifier.size(48.dp)` | Coil 按目标尺寸解码，不「下原图再缩」 |
| 避免在 item 里生成 lambda/对象 | 稳定引用（remember / 顶层） | 减少 GC 与无谓重组 |
| 分页/预取 | 数据侧分页加载（Modrinth API 支持 offset/limit） | 列表只持有可见 + 邻域数据 |

### 3.2b remember / derivedStateOf 用法

- `remember { ... }`：把值/对象绑定在 Composable 的 slot 上，**重组不重建**
  （只在 key 变化或配置变更时重建）。列表里典型用法：
  `val painter = remember(model) { ... }`。
  反例：每次重组都 `BitmapFactory.decode...` / 建 `OkHttpClient` / 建 lambda 闭包
  捕获大对象 —— 这些都应该 remember 或提到顶层。
- `derivedStateOf`：从其他 State 派生的值，**源没变就不重算、不触发下游重组**。
  典型：从 `List<DownloadItem>` 派生「当前 RUNNING 的进度百分比」——
  直接写 `val pct = list.first { it.state == RUNNING }?.progress`
  会在每次列表 emit（每 300ms 一次进度上报）时触发重组；
  包一层 `derivedStateOf { ... }` 后只有 pct 真变了才重组。
  本项目 DownloadService 的进度上报本来就是 300ms 节流，
  UI 侧再配 derivedStateOf / 把进度抽成子 Composable（ProjectCard 已做），
  重组范围被限制在单个卡片内。
- 判断标准：「这个值每次重组都要重算吗？重算贵吗？下游重组收益大吗？」
  三个都贵才值得 derivedStateOf；便宜的直接算。

### 3.3 图片解码（Coil 2.7.0，已对源码核实）

- **BitmapPool 在 Coil 2.0 已删除**（官方 changelog：API 23+ 收益小、
  不可变 bitmap 有性能优势）。所以 2.x 里**没有** `bitmapPool {}` builder，
  任务里「bitmap 池」一项落到 2.7.0 上就是不配（写了编译不过）。
- memoryCache：默认 `maxSizePercent` 按可用内存 25% 自动算；
  我们显式设 **50MB**（`MemoryCache.Builder(context).maxSizeBytes(Int)`，
  注意参数是 Int 字节数）。
- diskCache：Coil 2.7.0 的 API 是 `DiskCache.Builder().directory(File).maxSizeBytes(Long)`
  （3.x 才是 `sizeBytes`）。我们设 **128MB**，目录 `cacheDir/coil_disk_cache`。
- 注意本项目 `coil-compose:2.7.0` 的依赖里**没有 `coil`/`coil-singleton` 单例包**，
  所以 `AsyncImage` 必须显式传 `imageLoader` 参数（没有全局自动发现），
  ImageLoader 由 Hilt `@Singleton` 提供（见 `di/CoilModule.kt`），
  列表组件把它作为参数传下去。
- 尺寸裁剪靠「目标尺寸 + Coil 内部 inSampleSize/缩放解码」实现，
  Compose 侧只要把布局尺寸（如 48.dp）传给 AsyncImage 即可，不要自己
  预解码原图。

### 3.4 帧率与 jank

- 默认 60fps 即可，高刷屏不强制 120（见 3.1）。
- jank 的主要来源（按本项目排查优先级）：
  1. 列表 item 重组爆炸（key 不稳定 / 数据不是 data class）
  2. 大图解码进主线程堆（→ Coil memoryCache + 固定尺寸）
  3. GC 抖动（→ 避免 item 内新建对象；kotlinx 协程避免高频小分配）
  4. 布局测量昂贵（→ 固定行高）
- 观察工具：`adb shell cmd overlay enable-platform-overscroll-glow`（掉帧绿框）、
  `Layout Inspector`、`Macrobenchmark`（二期做帧时间 benchmark 时再上）。
- `enableEdgeToEdge()` 已开（MainActivity），注意给 Scaffold 留 insets padding，
  避免内容顶到状态栏被裁（现有 Screen 已用 Scaffold 处理）。

## 四、DownloadService 保活实现说明（对应本仓库代码）

- 类型：`dataSync` 前台服务（manifest 已声明 `foregroundServiceType="dataSync"`
  + 两个 FOREGROUND_SERVICE 权限 + POST_NOTIFICATIONS）。
- 启动时序（规避 12+ 后台启动限制）：
  1. UI 调 `DownloadManager.enqueue(...)`（App 必在前台）
  2. Manager 内部 `startForegroundService(intent)` → `onStartCommand` 里
     `startForeground(id, notification, FOREGROUND_SERVICE_TYPE_DATA_SYNC)`
  3. 通知栏持续有进度通知 = 厂商杀进程的最后防线
- 状态机在 `DownloadManager`（进程内单例 StateFlow），Service 只做执行 + 通知；
  进程活着时 Service 被回收状态不丢。**进程被杀则状态丢失**——
  跨进程死亡的断点续传留二期（WorkManager + Room 落库；
  当前不做的原因：下载是「会话内」场景，前台服务已覆盖切后台/锁屏，
  详见 `DownloadManager.kt` 头部注释）。
- 通知：同一 id 两态——运行中 ongoing + 进度条 + 暂停/取消操作（可点回 MainActivity）；
  全部结束转一次性通知（setAutoCancel）并退出前台、服务自毁。

## 五、Manifest / 权限 / 依赖 最终清单

**Manifest（已合并进 app/src/main/AndroidManifest.xml，增量）**：
```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_DATA_SYNC" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
...
<service
    android:name=".service.DownloadService"
    android:exported="false"
    android:foregroundServiceType="dataSync" />
```
（原 INTERNET / ACCESS_NETWORK_STATE / applicationName / activity 均未动）

**权限**：上面 3 个。POST_NOTIFICATIONS 运行时请求已在 MainActivity 实现（13+）。

**依赖**：**无需新增**。
- OkHttp：data 模块 `implementation("com.squareup.okhttp3:okhttp:4.12.0")`，
  app 已 `implementation(project(":data"))` → app 可传递使用。
- Coil / core-ktx / coroutines：app 已有。
- 若后续升级 Coil 到 3.x：API 变化大（`sizeBytes`、`bitmapPool` 回归与否、
  ImageLoader 默认发现方式），需单独评估。

## 六、ModBox 应该怎么做（结论清单）

1. 下载用 **dataSync 前台服务**（已实现），不要 WorkManager 起步。
2. 启动下载必须在**前台上下文**里做（用户点击时），规避 12+ 后台启动限制。
3. 13+ 启动时申请 **POST_NOTIFICATIONS**（已实现），拒绝后功能降级不崩溃。
4. 断点续传用 **Range + .part 临时文件**（已实现），sha512 对整体流式校验
   （续传时旧段先喂进 digest）。
5. 厂商差异：**不做自启动跳转**；下载页放一句「下载中断请检查电池优化策略」文案。
6. 列表渲染：**固定行高 + stable key/data + Coil 按目标尺寸解码**（已落地
   ProjectCard + CoilModule）。
7. 不锁 120Hz，默认帧率即可；jank 优先排查重组与大图解码。
8. Coil 全局 loader 由 **Hilt 单例提供**（本项目 coil-compose 2.7.0 没有
   singleton 自动发现，`AsyncImage` 必须显式传 `imageLoader`）。
9. 二期：WorkManager + Room 落库实现「进程被杀后续传」；Macrobenchmark 帧时间。
