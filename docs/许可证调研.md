# Modrinth 品牌 / 许可合规调研

- 调研日期：2026-11-28
- 调研人：license-agent（法务/合规调研员）
- 背景：本项目（modrinth-Android-beta，Kotlin/Compose 原生 Android 客户端，仅通过 HTTP 调 api.modrinth.com 公开 REST API）拟将 app 图标改为 **Modrinth 官方 Logo**、应用名改为「**modrinth APP**」。本文在落地前给出许可结论。
- 方法：GitHub API（`api.github.com`）+ raw.githubusercontent.com + modrinth.com 官网 / legal 页 + Flathub + support.modrinth.com。
- 网络限制记录：`api.modrinth.com` 的 `/v1/*` 对 datacenter IP 403（Cloudflare），但 `/openapi/v2.json` 200 可通（本调研所需信息均已拿到，未受阻塞）；modrinth.com 网页直连可达（`/terms` 旧路径 404，真实路径为 `/legal/terms` 等）。

## 一、结论速览（TL;DR）

| 事项 | 结论 | 风险等级 |
|---|---|---|
| 使用 Modrinth 官方 Logo（绿色圆环+扳手）作 app 图标 | **禁止**。Rinth, Inc. 书面声明「未经明确书面许可，严禁使用任何 Modrinth 品牌元素」，logo 文件被明确排除在所有开源许可之外（All rights reserved） | 🔴 高（版权+商标双重侵权，有明确成文禁止） |
| 应用名「modrinth APP」 | **不建议**。"Modrinth" 是公司明示保留的商标；且官方已存在同名产品「Modrinth App」（modrinth.com/app），近似命名+官方 logo 构成典型混淆/冒充。若必须提及，只能用描述性指称（如「Modrinth 客户端」「for Modrinth」）并显著声明非官方 | 🔴 高（配官方 logo 时）/ 🟡 中（仅描述性使用、无 logo 时） |
| 纯 HTTP 调用 labrinth（AGPL-3.0）公开 API | **安全**。不构成派生作品、不触发 AGPL 分发义务（详见 §4.1） | 🟢 低 |
| ZalithLauncher2（GPL-3.0）移植部分 | **大体合规但有三处缺口**：①部分文件未保留原作者版权头；②GLFW/zlib 许可声明被缩略（zlib 条款 3 要求原文保留）；③**因链接了 GPL 组件，整个 app 实质应作为 GPL-3.0 或更高版本分发**，而根 LICENSE 声明「MIT 仅约束 ModBox 自身代码」的写法与 GPL 强 copyleft 冲突，且分发时缺少 GPLv3 全文副本 | 🟡 中（可修复，修复成本低） |

**一句话建议**：官方 logo 和「modrinth APP」这个名字都不要用；继续用「ModBox」+ 自绘图标（勿模仿官方绿环+扳手造型），在描述里用「Modrinth 客户端（非官方）」这类描述性表述即可。

## 三、商标 / 名称风险分析（任务 2）

### 3.1 「modrinth APP」+ 官方 logo 的风险

1. **与官方产品正面撞名**：官方已有名为「Modrinth App」的产品（modrinth.com/app、Flathub 包名 `com.modrinth.ModrinthApp`）。我们叫「modrinth APP」+ 用官方 logo，在 Google Play / 侧载场景下构成典型的「冒充官方」外观，混淆可能性极高（名称+标识+品类三重重合）。
2. **商标**：ToS 明示 "Modrinth" 及相关名称、logo、口号均为 Rinth, Inc. 商标，「未经事先书面许可不得使用」。把「modrinth APP」当应用名（而非描述）属于商标性使用，不是描述性使用。
3. **Google Play 实操风险**：
   - Play 政策要求应用名不得侵犯他人知识产权、不得误导用户；权利人（Rinth）可走 Play 的商标投诉通道下架（Play 的 IP 政策对商标投诉响应很快）。
   - 官方 logo 被识别后（Play 审核有图像比对），会同时触发版权投诉。
   - 侧载渠道（官网 APK、各大论坛）不受 Play 审核保护，但同样面临 DMCA/商标函（ToS 与 COPYING 都留有「© Rinth, Inc.」主体，发函成本低）。
4. **即便只用 logo 不改名**，或**只改名不用 logo**，单独看各有一半风险，但两者叠加 = 高风险包。

**风险等级：🔴 高（强烈不建议）。** 这不是「能不能过审」的问题，而是对方有成文条款、有同名官方产品、有 Flathub 官方包在架，任何严肃分发都站不住。

### 3.2 替代命名建议（按推荐度排序）

| 方案 | 应用名（商店可见名） | 说明 | 风险 |
|---|---|---|---|
| ✅ 首选 | **ModBox**（维持现状，当前 `app_name` 已是 ModBox） | 自有名称，零商标冲突；描述里写「Modrinth 客户端（非官方）」。描述性提及「Modrinth」指向数据源属于 **nominative fair use**（指名用途：说明兼容/数据来源），是行业通行做法（类似「xxx for YouTube」） | 🟢 低 |
| 可选 | **Modrinth 客户端** / 「A Modrinth Client」/「for Modrinth」 | 「Modrinth」仅作描述性定语，**不得**配官方 logo、不得暗示官方/授权；商店描述中加一句「非官方，与 Rinth, Inc. 无关联/无授权」 | 🟡 中（可接受，描述性使用；但比 ModBox 多一层被投诉面，被投诉时靠 nominative use 抗辩） |
| 避免 | modrinth APP / Modrinth App / Modrinth 官方版 / 任何暗示官方身份的变体 | 商标性使用 + 冒充官方 | 🔴 高 |
| 避免 | 自制但模仿「绿环+扳手」造型的图标 | 复制对方 logo 的美术设计 = 同样侵权（即使不直接拷贝 SVG 文件） | 🔴 高 |

**图标**：自绘一个原创图标（建议保留「mod/模组」主题的自创图形，颜色上避开对方主色 `#81f3af`/`#033018` 的特定组合亦可，进一步降低混淆印象——这点是「降低混淆」的加分项而非硬性要求）。

**附带的包名问题（需 lead 决策，超出本次只调研范围）**：当前 `applicationId = "com.modrinth.android"` 也包含商标。Play 上架前建议评估改为如 `com.modbox.client`（注意：改 applicationId 会影响侧载用户的升级路径与 Play 账号绑定，需在首发 Play 前定下来）。这属于代码变更，不在本文档执行范围内。

## 四、我们的合规面（任务 3）

### 4.1 labrinth（AGPL-3.0）：纯 HTTP 调公开 API —— 结论：安全 🟢

理由（逐条）：

1. **没有复制/分发 labrinth 代码**：我们一行 labrinth 代码都没有，不 vendor 其 jar/依赖，app 内不含任何 AGPL 代码。AGPL 的义务（§4/§5/§13）都附加在「分发（convey）程序或其修改版」的行为上——我们什么都没分发（就 labrinth 而言）。
2. **纯网络调用不构成派生作品**：两个独立程序通过 REST API（JSON over HTTPS）通信，不共享内存、不链接、不共享 ABI。FSF 对「separate programs communicating over a network」的一贯立场是：这不产生结合作品（对比：动态库链接会产生）。我们的 app 只是「发送 HTTP 请求并解析响应」，与任何遵守 API 的第三方客户端（浏览器、Modrinth4J 用户）地位相同。
3. **AGPL §13（网络交互条款）不触发**：§13 约束的是「**运行（modified）该 AGPL 程序**并让用户通过网络交互」的人（即运行 labrinth 的人，如 Modrinth 自己或自托管者）。我们根本不运行 labrinth。
4. **官方姿态佐证**：org 官方维护 `Modrinth4J-fork`（MIT 客户端库，`https://github.com/modrinth/Modrinth4J-fork`），API v2 文档明示「recommended API for integrations and applications」——API 客户端是官方鼓励的生态，第三方 app 调 API 本身零风险。
5. **残留注意事项（低）**：
   - 不要在 app 里把 API 返回的项目数据**抓下来固化成本地静态数据库再分发**（那是在分发对方平台上的内容，涉及版权数据与 ToS 的再上传/再分发限制——`/legal/rules` 第 4 条要求内容上传需自有授权；动态在线获取则无此问题）。
   - 遵守 ToS 的使用条款与 Cloudflare 限流（当前 `/v1` 对 datacenter IP 403 只是对爬虫/机房 IP 的 WAF 策略，普通用户设备上的请求不受影响）。
   - 若将来引入 Modrinth4J（MIT）等官方库，MIT 下自由使用、保留其 NOTICE 即可。

### 4.2 ZalithLauncher2（GPL-3.0）移植部分 —— 结论：大体合规，3 处缺口需修复 🟡

**现状核对**（NOTICE 位于仓库根 `NOTICE`，移植代码位于 `app/src/main/java/com/modrinth/android/{keymap,ui/components/cardgrid,ui/components/colorpicker}`）：

✅ **已做对的**：
- NOTICE 写明源项目、源仓库 URL、许可（GPL-3.0 or later）、原作者（MovTery <movtery228@qq.com> 及贡献者，Copyright (C) 2025-2026）、逐文件移植映射表、适配说明、以及 zl2 依据 GPLv3 §7 的附加条款（改名、保留版权显示、不得捆绑其 ToS/隐私政策）。
- 每个移植文件头有 `// Ported from ZalithLauncher2 (GPL-3.0), see NOTICE`——满足 GPLv3 §5(a)「显著声明你修改了它」及来源可追溯。
- 未移植 zl2 的运行时/LWJGL 绑定部分（见 NOTICE），移植的是可分离的 Compose 组件。
- 名称合规：zl2 §7 条款 1 要求修改版不得含 "ZalithLauncher"/"ZL" 名称——我们用 ModBox，合规。（注：zl2 §7 条款 1 的「启动页标注非官方修改版」义务针对的是「ZalithLauncher 程序的修改版」；我们的 app 是**新程序**只是**包含**其组件，严格说该附加条款整体是否随组件移植而附着于我们的 app 存在解释空间——保守起见，在关于页注明「包含源自 ZalithLauncher2（GPL-3.0）的代码」即可同时覆盖。）

⚠️ **缺口 1（必须修）：部分移植文件丢掉了原作者版权头。**
GPLv3 §4 要求分发时「keep intact all notices」，原文文件的完整 GPL 头包含版权行：

```
/*
 * Zalith Launcher 2
 * Copyright (C) 2025-2026 MovTery <movtery228@qq.com> and contributors
 * …GPL 全文引用…
 */
```

逐一比对源文件（raw.githubusercontent.com/ZalithLauncher/ZalithLauncher2/main/...）后，**源文件带该头、而本地移植版只剩一行 "Ported from" 注释的文件**：

| 本地文件 | 源文件（均带完整 GPL+版权头） |
|---|---|
| keymap/GlKeyNames.kt | InputMap/.../keycodes/ControlEventKeyName.java |
| keymap/KeymapConfig.kt（默认键位部分） | InputMap/.../keycodes/_MinecraftKeyBindingMapper.kt |
| keymap/KeymapScreen.kt | ZalithLauncher/.../ui/control/Keyboard.kt + .../control_editor/edit_widget/KeyEventEdit.kt |
| keymap/AndroidKeyMapper.kt（映射表部分） | ZalithLauncher/.../game/input/EfficientAndroidLWJGLKeycode.java |
| cardgrid/engine/GridEngine.kt、model/*.kt（全部 7 个）、state/CardGridState.kt、ui/CardGrid.kt、ui/CardGridAutoScroll.kt（共 11 个） | CardGrid/src/main/kotlin/com/movtery/cardgrid/… 同路径文件 |

（ColorPicker 模块 9 个文件在**源仓库中本身就没有**版权头——源文件直接以 `package ...` 开头，如 Controller.kt / Utils.kt / ColorPicker.kt 等——所以 colorpicker 目录无头不是我们的问题，按 GPL 以仓库级 LICENSE + NOTICE 归属即可。）

**修法**：在上述文件头补回原文的版权+GPL 头（保留 `Ported from ... see NOTICE` 行在其后），即恢复「Zalith Launcher 2 / Copyright (C) 2025-2026 MovTery… / GPL 条款引用」注释块。这也同时满足 zl2 §7 条款 2「不得移除版权声明」。

⚠️ **缺口 2（应修）：GLFW/zlib 声明被缩略。**
`keymap/GlKeycodes.kt` 目前只有一行注释「键码常量取自 glfw3.h（GLFW 3.4，zlib 许可）」。但源文件 `InputMap/.../LwjglGlfwKeycode.java` 内嵌的是 **zlib 许可全文**，其条款 3 规定「This notice may not be removed or altered from any source distribution」（源分发中不得移除/改写本声明）。zlib 极为宽松（商用允许、仅需保留声明），风险低，但合规做法是把 zlib 许可声明（或至少第 3 条款原文）放进 `GlKeycodes.kt` 头注释或 NOTICE 附文。

⚠️ **缺口 3（结构性，必须正视）：整个 app 的许可定位。**
因为我们把 GPL-3.0 组件**编译链接进**了同一个 Android 应用，按 GPL 强 copyleft 规则，**整个 app 作为分发单元构成 GPL 组件的结合作品/派生作品，必须以 GPL-3.0 或更高版本许可分发**，并且：
- 根 `LICENSE`（MIT）声明「仅约束 ModBox 自身代码」的写法**不够**：app 不能整体是 MIT。正确表述应为：app 整体按 GPL-3.0+ 分发（NOTICE 可继续解释 MIT 文件与 GPL 文件的分层，但对外生效的许可是 GPL-3.0+）；
- **分发时须随附 GPLv3 许可全文副本**（GPLv3 §4：give all recipients a copy of this License along with the Program）——当前仓库只有 MIT 的 LICENSE，**缺 GPLv3 全文文件**（如 `LICENSE-GPLv3`），NOTICE 里只给了源仓库链接；
- 向 Play/侧载分发 APK 时须**提供（或显著声明提供渠道）app 的完整对应源代码**（含我们的 MIT 部分——此时它们一并按 GPL-3.0+ 对外），GPL 允许以书面要约+付费提供源码的形式满足（§4/§6，对「非源码形式分发」）。
- 若不愿整个 app 变 GPL：唯一干净的路是**解耦**（把三个 GPL 组件移出 app，重写为自有实现，或改用兼容许可的替代库），改动成本高，不建议为 logo/命名这类小需求做。
